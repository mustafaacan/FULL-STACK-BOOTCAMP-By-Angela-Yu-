
APPLICATION PROGRAM INTERFACE (API)

These are structures used for data exchange between programs with different or similar architectures. Kind of Brigde
One of the best things about it is that we don’t need to worry about the architecture or database structure of the applications we’re working with.
We just need to know how to send a request and what the response will be.

IOT architectures also can use API structures.

################################################################

API TYPES ACCORDING TO SCTRUCTURE

1. GraphQL (QUERYING LANGUAGE) --> It is an open-source data querying and processing language developed for APIs 
               It allows clients to request only the data they need—and nothing more—from the server.
               client receives only the data it needs.
               Scenario: Requesting only a user's name and email address

2. SOAP (PROTOCOL) --> (Simple Object Access Protocol) is an XML-based communication protocol that enables applications 
             written in different platforms and languages to securely exchange data over a network.
             In corporate systems that require strict rules and high security.
             Scenario: A bank sends a request to transfer funds to another bank in XML format.

3. REST API (ARCHITECTURE / USING HTTP PROTOCOL) --> It is an architecture that enables different software systems to communicate with each other 
                               securely over the Internet according to standard rules. It allows data (typically in JSON format) 
                               to be sent and received using the HTTP PROTOCOL. 
                               Common in simple web and mobile apps.
                               Scenario: Retrieve user number 5 as JSON using the GET /users/5 request.

4. gRPC (RPC FRAMEWORK) --> It is an open-source Remote Procedure Call (RPC) framework developed by Google that enables 
            high-performance, low-latency communication between different programming languages.
            For fast communication between microservices.
            Scenario: Microservices quickly querying inventory information.






API TYPES ACCORDING TO USAGE PURPOSE

1. Public/Open API --> These are APIs that are available to everyone (including external developers) 
                        over the Internet and are typically accessible via authentication
                        Example: A weather application retrieves Istanbul’s current temperature from a weather API

2. Private/Internal API --> These are APIs that are used solely for data sharing within a company’s or organization’s 
                            internal departments and systems and are not accessible externally
                            Example: A company’s internal application retrieves employee leave information from its database


3. Partner API --> This is a type of API provided to authorized individuals for the purpose of securely 
                    exchanging data between the systems of companies that have specific business partners
                    An e-commerce platform checks delivery information through its shipping partner’s API

4. Composite API --> These are APIs that combine multiple APIs or data sources into a single call to meet 
                    complex system requirements
                    Example: A single API request checks inventory, processes the payment, and creates a shipment.

RATE LIMITING

a technique used to control the number of requests a client can make to a server within a set time period.
Usually remaining rate limit can be seen inside the response's header.

Request tracking: The server identifies clients using an IP address, user ID, or API key.
Threshold comparison: It checks recent usage against the allowed maximum.
Rejection: If a client goes over the limit, the server blocks extra requests and sends back a "429 Too Many Requests" status code

AUTHENTICATION vs. AUTHORIZATION

For Course: https://www.udemy.com/course/the-complete-web-development-bootcamp/learn/lecture/38912024?start=0#overview

Authentication: Answers the question “Who are you?” It verifies the user’s identity.
Example: Logging in with a username and password.

Authorization: Answers the question “What are you allowed to do?” It checks the authenticated user’s permissions.
Example: Only an admin can delete another user’s account.

Authentication verifies identity; authorization verifies permissions.

Login → Authentication → Authorization → Resource

Real-life example: Using an ID card to enter a company building is authentication. 
Being allowed to enter only specific rooms is authorization.


Does the request contain a valid token? → Authentication
Does the user have the admin role?      → Authorization
Can the user modify this specific item? → Authorization

If authentication credentials are missing or invalid, the server generally returns:
401 Unauthorized
Despite its name, 401 Unauthorized normally represents an authentication problem.
If the user is authenticated but does not have permission to perform the operation, the server generally returns:
403 Forbidden

API keys are generally used to:
Identify an application or project
Authenticate server-to-server communication
Track API usage
Apply rate limits and quotas
Restrict access to specific APIs
API keys are often long-lived. If an API key is stolen, an attacker may continue using it until it is revoked or replaced.
API keys should not be:
Hard-coded in frontend JavaScript
Embedded in publicly distributed applications
Committed to Git repositories
Included directly in URLs
Written to application logs
Environment variables or secret-management systems should be used to store them.

Bearer means that whoever possesses the token may be able to use it. Therefore, bearer tokens must be protected carefully.

Token-based systems commonly use:
A short-lived access token
A longer-lived refresh token
Roles and permission scopes
Token expiration
Token rotation and revocation mechanisms


** For basic authentication methods, to increase the security level, the other option is using
    HTTPS instead of HTTP

HTTP + TLS = HTTPS
When an API key or token is sent over HTTPS, TLS provides three important protections:
Confidentiality: Third parties on the network cannot easily read the request or its credentials.
Integrity: Attackers cannot easily modify requests or responses during transmission.
Server authentication: The TLS certificate helps the client verify that it is communicating with the correct server.

HTTPS
└── Protects the communication channel
    └── HTTP request
        ├── API key or token → Helps identify the requester
        └── Roles or scopes  → Determine allowed operations

API key or token: Who is making the request?
Authorization rules: What is the requester allowed to do?
HTTPS: How are the credentials and data transported securely?


In a production environment, an API that uses API keys or tokens should always use HTTPS. 
Credentials should be sent through headers, kept out of URLs and logs, 
rotated when appropriate, and limited to the minimum permissions required.

PASSING OBJECTS TO EJS: SHORTHAND, RENAMING, AND NESTING

The second argument of res.render() is an object containing template locals.
Its property names determine how you access the values inside EJS.
These are ordinary JavaScript object rules, not special EJS syntax.

1. Property shorthand: { genre, sort }

const genre = "rock";
const sort = "name";

res.render("bands", { genre, sort });

This is exactly equivalent to:

res.render("bands", {
  genre: genre,
  sort: sort
});

The property names and variable names are the same, so JavaScript allows
the shorter form. Access each value directly in views/bands.ejs:

<p>Genre: <%= genre %></p>
<p>Sort: <%= sort %></p>

2. Renaming a value: { data: genre }

res.render("bands", { data: genre });

The key on the left (data) is the name available in the template.
The expression on the right (genre) supplies its value.
Because genre is "rock", data is also the string "rock":

<p><%= data %></p>

Do not use data.genre here: data is a string, not an object with a genre
property. The variable genre is not separately passed by this render call.

3. Grouping values inside a nested object

res.render("bands", {
  data: {
    genre,
    sort
  }
});

Now data is an object: { genre: "rock", sort: "name" }.
Access its properties through data in EJS:

<p>Genre: <%= data.genre %></p>
<p>Sort: <%= data.sort %></p>

You can also create the object first:

const filters = { genre: "rock", sort: "name" };
res.render("bands", { data: filters });

This also supports data.genre and data.sort because filters is an object.
Therefore, { data: genre } could support data.genre only if the variable
named genre itself held an object containing a genre property.

KEY TAKEAWAY

data is not a reserved EJS keyword in these examples; it is a chosen key.
You could use filters, band, or another suitable name instead.

{ genre, sort }                 -> EJS: genre and sort
{ data: genre }                 -> EJS: data (the value of genre)
{ data: { genre, sort } }       -> EJS: data.genre and data.sort

Choose direct locals for simple values and nested objects when grouping
related data makes the template clearer. Match EJS access to the actual
shape of the object you pass.

SERVER-SIDE AXIOS, AUTHENTICATION, AND ALTERNATIVES

WHY USE AXIOS ON THE SERVER?

Axios is an HTTP client: it helps your server send requests to another API.
Express handles incoming requests; Axios sends outgoing requests.

Example flow in an EJS application:

Browser -> Express -> Axios -> External activity API
              |
              -> Render EJS with the API data -> Send HTML to the browser

import axios from "axios";

app.get("/", async (req, res) => {
  try {
    const response = await axios.get("https://api.example.com/activities", {
      timeout: 5000,
    });

    res.render("index.ejs", { data: response.data });
  } catch (error) {
    res.status(502).send("Could not retrieve activities.");
  }
});

The example URLs are placeholders. Replace them with actual API endpoints.

Benefits of making API requests on the server:
- Keep secret API keys on the server instead of exposing them in browser code.
- Filter and transform API data before passing it to an EJS template.
- Combine results from multiple APIs.
- Centralize headers, timeouts, and error handling.

AUTHENTICATION WITH AXIOS

Axios can send credentials, but the receiving server verifies them.
Axios does not create a user authentication system by itself.
The following examples use environment variables for secret values.
Do not expose those values in rendered HTML or commit them to source control.
Send credentials over HTTPS.

1. BASIC AUTHENTICATION

Use the auth option to send a username and password with HTTP Basic Auth:

const response = await axios.get("https://api.example.com/profile", {
  auth: {
    username: process.env.API_USERNAME,
    password: process.env.API_PASSWORD,
  },
});

The auth option is specifically for Basic Auth. It sets the Authorization
header and overrides a custom Authorization header in the same request.

2. BEARER TOKEN

Send an access token in the Authorization header. A JWT can be used this way,
but not every Bearer token is a JWT.

const response = await axios.get("https://api.example.com/profile", {
  headers: {
    Authorization: `Bearer ${process.env.API_TOKEN}`,
  },
});

3. API KEY

Use the header name required by the API documentation:

const response = await axios.get("https://api.example.com/activities", {
  headers: {
    "x-api-key": process.env.API_KEY,
  },
});

The API determines the key's name and location. Some APIs require a header;
others require a query parameter or another format.

4. OAUTH

Axios can make the HTTP requests needed to obtain or refresh an access token
and then send that token in subsequent requests. The OAuth flow must be
implemented separately or handled by an appropriate authentication library.

ALTERNATIVE: BUILT-IN FETCH

Modern Node.js versions include fetch(), so basic HTTP requests do not
require an additional package.

const response = await fetch("https://api.example.com/activities", {
  headers: {
    Authorization: `Bearer ${process.env.API_TOKEN}`,
  },
});

if (!response.ok) {
  throw new Error(`API error: ${response.status}`);
}

const data = await response.json();

AXIOS VS FETCH

Installation:
- Axios: install a separate package (npm install axios).
- Fetch: included in modern Node.js versions.

JSON responses:
- Axios: JSON responses are normally parsed automatically; use response.data.
- Fetch: explicitly parse the response with await response.json().

HTTP errors such as 404 and 500:
- Axios: rejects the promise by default, so try/catch handles these responses.
  This behavior can be customized with validateStatus.
- Fetch: does not reject just because of an HTTP error status. Check
  response.ok or response.status yourself. Network failures can still reject.

Both can send authentication headers. For a simple activity API application,
either option works; Axios is a convenience rather than a requirement.




AXIOS METHODS AND ARGUMENT ORDER

Axios supports GET, POST, PUT, PATCH, and DELETE. The API determines which
methods are supported and what each endpoint does.

For POST, PUT, and PATCH, the argument order is URL, body, then config:

axios.post(url, data, config);
axios.put(url, data, config);
axios.patch(url, data, config);

await axios.post(
  "https://api.example.com/activities", // URL
  { activity: "Read a book", participants: 1 }, // Request body
  {
    headers: { Authorization: `Bearer ${process.env.API_TOKEN}` },
    params: { language: "en" }, // URL query parameters, not the body
    timeout: 5000,
  } // Request configuration
);

Typical uses: POST creates a resource, PUT replaces a resource, PATCH updates
selected fields, GET retrieves data, and DELETE removes a resource.

GET and DELETE take config as the second argument:

await axios.get(url, { params: { type: "education" } });
await axios.delete(url);

If a DELETE endpoint requires a body, put it in config.data:

await axios.delete(url, {
  data: { id: 2 },
  headers: { Authorization: `Bearer ${process.env.API_TOKEN}` },
});

Express app.post() handles an incoming request; axios.post() sends an
outgoing request. Handle Axios failures with try/catch in async code.

AXIOS REQUEST INTERCEPTORS

A request interceptor runs before Axios sends a request. It can inspect or
modify the request configuration before the request is sent.

axios.interceptors.request.use((request) => {
  // Request headers, such as Authorization and Content-Type.
  console.log("Headers:", request.headers);

  // Basic Auth configuration: { username, password }.
  console.log("Auth config:", request.auth);

  // Query parameters that Axios will add to the URL.
  console.log("Query params:", request.params);

  // The configured URL or path, such as "/activities".
  console.log("Request URL:", request.url);

  // The HTTP method, such as "get" or "post".
  console.log("Request Method:", request.method);

  // Return the configuration so Axios can continue processing the request.
  return request;
});

This logging example is for learning with dummy credentials. Headers, auth,
query parameters, and URLs can contain secrets or personal data. Omit or
redact sensitive values when logging real requests.

EXAMPLE REQUEST

await axios.get("https://api.example.com/activities", {
  params: { type: "education" },
  auth: {
    username: "demo",
    password: "example",
  },
});

Selected interceptor output:

Auth config: { username: 'demo', password: 'example' }
Query params: { type: 'education' }
Request URL: https://api.example.com/activities
Request Method: get

IMPORTANT DETAILS

- request is Axios's request configuration object, not Express's req object.
  The callback parameter could also be named config.
- request.auth contains Basic Auth options. A Bearer token normally belongs
  in request.headers.Authorization, not request.auth.
- request.url is not necessarily the final URL. Query parameters may not yet
  be appended, and a relative path may be combined with baseURL later.
- Some configuration fields may be undefined if they were not provided.
- This callback must return a valid configuration (or a promise resolving
  to one). Omitting the return does not provide Axios with that configuration
  and can cause the request to fail.

MODIFYING A REQUEST

An interceptor can add a shared header before returning the configuration:

axios.interceptors.request.use((request) => {
  request.headers["X-App-Name"] = "My Activity App";
  return request;
});

CUSTOM API CLIENTS

An interceptor registered on the default axios client is not automatically
registered on clients created with axios.create(). Register it on the
specific client you use:

const activityApi = axios.create({
  baseURL: "https://api.example.com",
  timeout: 5000,
});

activityApi.interceptors.request.use((request) => {
  request.headers["X-App-Name"] = "My Activity App";
  return request;
});

// This request passes through activityApi's request interceptor.
const activityResponse = await activityApi.get("/activities");
